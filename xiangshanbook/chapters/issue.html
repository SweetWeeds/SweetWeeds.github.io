Chapter 07

디스패치·이슈·실행

리네임을 마친 명령어는 곧바로 실행되지 않는다. 먼저 자기를 실행할 수 있는 실행 유닛 앞의 이슈 큐(issue queue)에 들어가 기다린다. 피연산자가 모두 준비되는 순간 큐에서 뽑혀 레지스터 파일을 읽고, 실행 유닛을 지나 결과를 쓴다. 비순차 코어의 속도는 이 "기다렸다가 준비되면 바로 출발" 과정을 얼마나 촘촘하게 돌리느냐에 달렸다. XiangShan 곤명호 v3는 정수·부동소수·벡터 세 스케줄러에 이슈 큐 23개를 두고, 결과가 나오기도 전에 다음 명령을 미리 깨우는 투기적 웨이크업을 쓴다.

  • 정수·부동소수·벡터 스케줄러의 이슈 큐 구성과 각 큐에 붙은 실행 유닛을 실제 설정에서 읽어 낸다.
  • 디스패치가 같은 종류의 이슈 큐 여러 개에 명령을 나눠 주는 균형 정책을 시뮬레이터로 비교한다.
  • 나이 행렬로 "준비된 것 중 가장 오래된 명령"을 한 사이클에 고르는 원리를 직접 조작해 본다.
  • 투기적 웨이크업과, 적재가 빗나갔을 때의 취소·재발행을 사이클 단위로 따라간다.
  • 레지스터 파일 읽기 포트 공유와 우선순위 때문에 생기는 발행 실패를 확인한다.

스케줄러 지도

XiangShan의 백엔드는 토마술로 알고리즘(Tomasulo)의 직계 후손이다(backend/README.md가 직접 이 논문을 인용한다). 리네임된 명령어는 디스패치(Dispatch)에서 기능 유닛 종류(FuType)를 보고 알맞은 이슈 큐로 보내진다. 이슈 큐는 세 스케줄러로 묶인다. 정수 스케줄러에 13개, 부동소수 스케줄러에 4개, 벡터 스케줄러에 6개다. 큐마다 실행 유닛(EXU)이 하나나 둘 붙고, 실행 유닛 하나는 여러 기능 유닛(FU)을 품는다. 예를 들어 첫 정수 큐는 ALU0과 BJU0 두 실행 유닛에 명령을 내보낸다. ALU0 안에는 ALU, CSR, Fence, Link가, BJU0 안에는 분기와 점프가 들어 있다.

디스패치: 어느 큐로 보낼까

ALU 명령은 여섯 개 큐(IQ0~IQ5) 중 어디로 가도 실행될 수 있다. 적재는 세 큐(IQ6~IQ8) 중 어디로 가도 된다. 이렇게 같은 종류를 받는 큐가 여럿일 때, 디스패치는 지금 덜 찬 큐부터 채운다. Dispatch.scala는 큐마다 차 있는 엔트리 수를 비교해 큐들을 정렬해 두고, 한 묶음 안의 i번째 ALU 명령을 i번째로 덜 찬 큐로 보낸다. 큐마다 들어오는 칸이 두 개(numEnq = 2)라서, 한 사이클에 한 큐로는 최대 두 명령까지만 들어갈 수 있다.

가장 오래된 준비된 명령 고르기

이슈 큐는 매 사이클 "피연산자가 모두 준비되었고, 아직 발행되지 않았고, 막혀 있지 않은" 엔트리를 찾는다(EntryBundles.scala:40-42의 canIssue). 여러 개라면 그중 가장 오래된 것을 고른다. 오래된 명령은 ROB 머리에 가깝다. 먼저 끝내야 커밋이 막히지 않고, 그 뒤에 줄 선 명령들도 깨울 수 있다.

"가장 오래된"을 한 사이클 안에 찾기 위해 XiangShan은 나이 행렬(age matrix)을 쓴다. N개 엔트리마다 "i가 j보다 먼저 들어왔다"는 비트 age(i)(j)를 저장한다. 엔트리 i는 자기보다 오래된 준비된 엔트리가 하나도 없을 때 선택된다. 행렬은 대각선을 기준으로 대칭(서로 반대)이라 위 삼각형만 레지스터로 둔다.

$$\text{oldest}_i = \text{canIssue}_i \;\land\; \bigwedge_{j} \big(\text{age}(i,j) \lor \lnot\,\text{canIssue}_j\big)$$
age(i,i) = 1, i < j면 age(i,j)를 레지스터에서 읽고, i > j면 ¬age(j,i)로 대신한다. 새 엔트리 i가 들어오면 i행은 모두 0(가장 젊음), i열은 모두 1로 바뀐다(AgeDetector.scala:60-84).
getOldestCanIssue 
// src/main/scala/xiangshan/backend/issue/AgeDetector.scala:92-96
def getOldestCanIssue(get: (Int, Int) => Bool, canIssue: UInt): UInt = {
  VecInit((0 until numEntries).map(i => {
    (VecInit((0 until numEntries).map(j => get(i, j))).asUInt | ~canIssue).andR & canIssue(i)
  })).asUInt
}

실제 큐는 엔트리를 세 무리로 나눈다. 디스패치에서 막 들어온 명령은 들어오는 칸(enq entry, 2개)에 머문다. 그 뒤 복합 칸(complex entry)으로 옮겨지는데, 자리가 없으면 단순 칸(simple entry)에 들렀다 간다. 선택은 무리마다 따로 나이 행렬로 한다. 그리고 복합 칸에서 뽑힌 것이 있으면 그것, 없으면 단순 칸, 그다음 들어오는 칸 순으로 고른다(IssueQueue.scala:573-582). 오래 머문 명령일수록 복합 칸에 있을 가능성이 크므로, 이 순서는 대체로 "오래된 것 먼저"를 지키면서 비교기 수를 줄인다.

빈 칸을 누르면 그 칸에 명령이 들어오고, 찬 칸을 누르면 준비 상태가 바뀐다.

미리 깨우기와 취소

소비자 명령은 생산자의 결과가 레지스터 파일에 쓰인 뒤에야 준비되는 것일까? 그렇게 하면 한 사이클짜리 덧셈 사슬도 매 명령마다 몇 사이클씩 쉬어야 한다. XiangShan은 생산자가 발행되는 순간 그 지연 시간을 알고 있으므로, "몇 사이클 뒤에 결과가 나온다"는 사실만으로 소비자를 미리 깨운다. 이것이 이슈 큐 사이의 웨이크업(IQ wakeup)이다. 결과 자체는 실행 유닛 출구의 바이패스 네트워크(BypassNetwork)로 바로 전달되므로, 지연 0인 ALU끼리는 매 사이클 연달아 발행할 수 있다. 어떤 실행 유닛이 어떤 큐를 깨울 수 있는지는 Parameters.scala:556-576의 iqWakeUpParams가 정한다. 정수 ALU 6개와 적재 3개는 정수 쪽 모든 큐를 깨우고, 적재는 부동소수 큐도 깨운다.

문제는 적재다. 적재의 지연 시간은 캐시 적중 여부에 달렸는데, 발행 시점에는 그걸 모른다. XiangShan은 적재가 적중한다고 가정하고 정해진 지연 값(LduCfg의 UncertainLatency(3))으로 소비자를 깨운다. 나중에 적재 파이프라인이 미스를 알게 되면 ld1Cancel이나 ld2Cancel 신호를 낸다. 그 적재 결과를 믿고 이미 발행된 명령은 취소되고, 이슈 큐에 남아 있던 엔트리가 다시 '발행 안 됨'으로 돌아간다. 엔트리는 피연산자마다 2비트 loadDependency를 들고 다닌다. 그 비트로 "몇 사이클 전 어느 적재 파이프의 결과에 기대고 있는지"를 알아, 취소 신호가 오면 자기가 대상인지 판단한다.

LoadShouldCancel 
// src/main/scala/xiangshan/backend/Bundles.scala:1838-1844
object LoadShouldCancel {
  def apply(loadDependency: Option[Seq[UInt]], ldCancel: Seq[LoadCancelIO]): Bool = {
    val ld1Cancel = loadDependency.map(_.zip(ldCancel.map(_.ld1Cancel)).map { case (dep, cancel) => cancel && dep(0)}.reduce(_ || _))
    val ld2Cancel = loadDependency.map(_.zip(ldCancel.map(_.ld2Cancel)).map { case (dep, cancel) => cancel && dep(1)}.reduce(_ || _))
    ld1Cancel.map(_ || ld2Cancel.get).getOrElse(false.B)
  }
}

답 보기

적재는 대부분 L1 캐시에 적중한다. 적중을 기다렸다 깨우면 모든 적재 소비자가 매번 몇 사이클씩 늦어진다. 반면 투기적으로 깨우면 손해는 드문 미스 때만 본다. 위 시뮬레이터에서 '적중'일 때 두 정책의 마지막 사이클 차이를 보면, 매 적재마다 얼마를 아끼는지 알 수 있다.

레지스터 파일 읽기: OG0와 OG1

이슈 큐에서 뽑힌 명령은 곧바로 실행 유닛으로 가지 않고 DataPath를 지난다. 첫 단계 OG0에서 레지스터 파일 읽기 포트를 중재받고, 둘째 단계 OG1에서 읽은 값을 받아 실행 유닛에 넘긴다. 정수 레지스터 파일은 물리 레지스터 224개, 4뱅크다(Parameters.scala:121-126). 읽기 포트는 12개(0~11번)뿐인데, 정수 쪽 실행 유닛이 원하는 피연산자는 그보다 많다. 그래서 포트 하나를 여러 실행 유닛이 우선순위를 두고 나눠 쓴다. IntRD(7, 2)는 "7번 포트를 우선순위 2로"라는 뜻이고, 숫자가 작을수록 먼저다.

중재에서 진 명령은 OG0에서 실패 응답(og0Resp.failed)을 받는다. 이슈 큐 엔트리는 '발행됨'을 지우고 다음 사이클에 다시 경쟁한다. 실행 유닛이 받을 수 없는 상태(나눗셈기처럼 파이프라인이 아닌 유닛이 바쁠 때)면 OG1에서 실패한다.

왜 포트를 그냥 늘리지 않을까

레지스터 파일의 면적과 지연은 포트 수에 따라 가파르게 커진다. 셀마다 포트 수만큼 단어선과 비트선이 지나가야 하기 때문이다. XiangShan은 ALU의 첫째 피연산자와 적재 주소에는 우선순위 0 포트를 주고, 분기·스토어 피연산자와 일부 ALU의 둘째 피연산자는 그 포트를 낮은 우선순위로 빌려 쓰게 했다. 또 값이 최근에 쓰였다면 작은 레지스터 캐시나 바이패스에서 꺼내 포트를 아예 쓰지 않게 했다.

기능 유닛의 지연과 처리량

실행 유닛 안의 기능 유닛은 두 성질로 나뉜다. 지연이 정해진(CertainLatency) 유닛과 정해지지 않은(UncertainLatency) 유닛이다. 그리고 파이프라인(piped)이라 매 사이클 새 명령을 받는 유닛과, 하나를 끝낼 때까지 바쁜 유닛이 있다. 지연이 정해진 유닛은 이슈 큐가 미리 소비자를 깨울 수 있다. 나눗셈기처럼 정해지지 않은 유닛은 결과가 나와야 깨울 수 있다.

쓰기 쪽에도 경쟁이 있다. 정수 레지스터 파일의 쓰기 포트는 9개다. ALU0~5가 0~5번, LDU0~2가 6~8번을 쓴다. 그런데 부동소수 FEX0(FCMP·FCVT 결과)은 3번 포트를, 벡터 VFEX0은 4번 포트를 우선순위 1로 함께 쓴다(IntWB(port = 3, 1) 등). 이렇게 공유된 쓰기 포트에서 두 결과가 부딪칠 것 같으면 DataPath의 쓰기 충돌 검사기(IntRFWBCollideChecker 등)가 OG0에서 진 쪽을 실패시킨다. 또 한 실행 유닛 안에서도 지연이 다른 기능 유닛(예: ALU4의 ALU와 MUL)의 결과가 같은 사이클에 출구로 나오면 안 된다. 그래서 이슈 큐는 FuBusyTable로 그 실행 유닛 출구가 몇 사이클 뒤에 쓰일지 기억해 두고, 겹칠 엔트리는 발행 후보에서 뺀다(IssueQueue.scala:430-433).

핵심 정리

  1. 곤명호 v3의 이슈 큐는 정수 13개, 부동소수 4개, 벡터 6개다. 큐마다 실행 유닛 1~2개가 붙고, 모든 구성은 Parameters.scala의 IssueBlockParams 몇 줄로 정해진다.
  2. 같은 종류를 받는 큐가 여럿이면 디스패치는 점유가 낮은 큐부터 채워 부하를 고르게 한다.
  3. 이슈 큐는 나이 행렬로 준비된 것 중 가장 오래된 명령을 한 사이클에 고른다. 엔트리는 들어오는 칸, 단순 칸, 복합 칸으로 나뉘고, 고를 때는 복합 칸이 앞선다.
  4. 지연이 정해진 생산자는 발행 즉시 소비자를 깨운다. 적재는 적중을 가정해 깨웠다가, 미스면 ld1Cancel/ld2Cancel로 소비자를 취소하고 다시 발행한다.
  5. 레지스터 파일 읽기 포트는 우선순위를 두고 공유된다. 중재에서 진 명령은 OG0에서 실패해 큐로 돌아가 다시 경쟁한다.

확인 퀴즈

Q1. 정수 큐 IQ0(엔트리 18, numEnq 2, numComp 10)의 단순 칸은 몇 개인가?

numSimp = numEntries − numEnq − numComp(IssueBlockParams.scala:167)이므로 18 − 2 − 10 = 6이다.

Q2. 나이 행렬에서 새 명령이 칸 i로 들어올 때 일어나는 일은?

새로 들어온 명령은 누구보다도 젊다. 그래서 "i가 j보다 오래됨"은 모두 거짓이고, "j가 i보다 오래됨"은 모두 참이 된다.

Q3. 적재를 믿고 발행된 소비자가 취소되는 계기는?

적재가 미스로 판명되면 적재 파이프라인이 취소 신호를 내고, loadDependency로 그 적재에 기댄 것으로 표시된 엔트리가 발행을 취소한다.

Q4. 7번 정수 읽기 포트는 LDU0(우선순위 0), ALU3(1), BJU0(2)이 함께 쓴다. 셋이 같은 사이클에 요청하면?

설정의 우선순위 숫자가 작은 쪽이 이긴다. 진 실행 유닛은 실패 응답을 받고 다음 사이클에 다시 시도한다.

Q5. 나눗셈기(DivCfg)의 설정으로 옳은 것은?

FuConfig.scala:367-376: piped = false, latency = UncertainLatency(). 그래서 미리 깨울 수 없고, 하나를 끝낼 때까지 다음 명령을 받지 않는다.
