Chapter 15

검증과 시뮬레이션

XiangShan은 Chisel 코드다. 코드를 고친 뒤 칩이 여전히 맞게 도는지 확인하려면 그 코드를 먼저 돌릴 수 있는 무언가로 바꿔야 한다. Chisel을 SystemVerilog로 내리고, Verilator가 그것을 C++ 시뮬레이터 emu로 만든다. emu가 명령을 하나 끝낼 때마다 참조 모델 NEMU도 같은 명령을 실행한다. 둘의 결과가 처음 어긋나는 순간이 바로 버그가 드러나는 지점이다. 이 장은 kunminghu-v3 저장소에 들어 있는 그 도구들, 즉 빌드 흐름, DiffTest, LightSSS, 체크포인트, 관찰 도구, CI를 차례로 연다.

  • make verilog·sim-verilog·emu가 Chisel을 어떤 단계를 거쳐 실행 파일로 만드는지, 단계마다 무엇이 나오는지 따라간다.
  • DiffTest가 커밋마다 참조 모델과 무엇을 비교하는지, 어떤 프로브(DiffXXX)가 어떤 아키텍처 상태를 지키는지 짚어 본다.
  • emu 실행 옵션을 조립하고, 함께 쓰면 안 되는 옵션 조합을 확인한다.
  • LightSSS가 fork로 스냅숏을 남겨, 실패 직전 구간만 파형과 함께 다시 돌리는 원리를 시간축 위에서 본다.
  • 체크포인트와 SimPoint 가중 평균으로 긴 프로그램의 CPI를 몇 구간만 돌려 추정하는 방법을 실험한다.

Chisel에서 emu까지

XiangShan 저장소의 최상위 Makefile에는 세 가지 핵심 목표가 있다. make verilog는 실제 칩용 최상위 XSTop의 RTL을, make sim-verilog는 시뮬레이션용 최상위 SimTop의 RTL을 만든다. make emu는 sim-verilog 결과를 difftest 서브모듈의 Makefile에 넘겨 Verilator로 컴파일한다. 빌드 도구는 mill이고, Chisel 코드를 엘라보레이션해 FIRRTL을 얻은 뒤 CIRCT의 firtool이 그것을 SystemVerilog로 내린다.

옵션

한 걸음씩 맞추기: DiffTest

비순차 코어는 수백 개의 명령을 동시에 들고 있다. 버그가 있으면 잘못된 값이 레지스터 몇 개를 거쳐 한참 뒤에야 엉뚱한 곳에서 드러난다. 그래서 XiangShan은 DiffTest(differential testing)로 검증한다. emu가 명령을 하나 커밋할 때마다, 참조 모델(REF)도 같은 명령을 한 걸음 실행한다. 그다음 두 쪽의 아키텍처 상태를 비교한다. 이를 lock-step 공동 시뮬레이션이라 한다. 기본 REF는 NEMU다. NEMU_HOME/build/riscv64-nemu-interpreter-so를 공유 라이브러리로 열고, Spike를 쓰도록 바꿀 수도 있다(difftest/src/test/csrc/difftest/refproxy.cpp:342-348). 경로는 --diff로 직접 줄 수도 있다.

RTL 안에서 비교할 값을 내보내는 장치를 프로브라 한다. 프로브는 DifftestModule(new DiffInstrCommit ...)처럼 설계 곳곳에 심는다. ROB는 커밋한 명령을, CSR 모듈은 CSR 상태와 예외를, 스토어 버퍼는 메모리에 쓴 값을 내보낸다. 처음 어긋나는 순간 시뮬레이션은 멈추고, 어긋난 명령의 PC와 값을 보고한다. 프로그램이 끝까지 어긋나지 않고 종료 명령에 닿으면 HIT GOOD TRAP이 찍힌다. 아래에서 작은 프로그램에 버그를 하나 심어 보자.

      어떤 프로브가 무엇을 지키는가

      difftest 서브모듈 README의 API 표에서 필수로 표시된 프로브는 다섯 가지다. DiffArchEvent(예외·인터럽트), DiffInstrCommit(커밋한 명령), DiffTrapEvent(시뮬레이션 종료 호출), DiffCSRState(CSR), DiffPhyIntRegState(정수 레지스터)다. 나머지는 선택이다. kunminghu-v3는 물리 레지스터가 32개보다 많다. 그래서 물리 레지스터 파일 전체(DiffPhyIntRegState)와 리네임 테이블(DiffArchIntRenameTable)을 함께 보내고, C++ 쪽이 둘을 맞춰 아키텍처 레지스터 값을 복원한다. 아래 표에서 행이나 칸을 눌러 각 프로브가 kunminghu-v3의 어느 모듈에 심겨 있는지 확인하자.

      ROB가 커밋을 알리는 곳

      커밋 폭만큼 DiffInstrCommit을 만든다. index는 그 사이클의 몇 번째 커밋인지를 뜻한다. MMIO처럼 REF가 흉내 낼 수 없는 명령은 skip으로 표시해 REF가 결과를 DUT에서 복사하게 한다. 이동 제거된 명령(eliminatedMove)은 건너뛰지 않는다.

      // src/main/scala/xiangshan/backend/rob/Rob.scala:1743-1755
val difftest = DifftestModule(new DiffInstrCommit(diffMaxPhyRegs), delay = 3, dontCare = true)
val dt_skip = Mux(eliminatedMove, false.B, exuOut.isSkipDiff)
difftest.coreid := io.hartId
difftest.index  := i.U

      스쿼시: 여러 커밋을 한 번에 비교하기

      커밋마다 C++로 건너가 비교하면 시뮬레이션이 느려진다. difftest는 연속한 커밋 여러 개를 하드웨어 쪽에서 하나로 합쳐(squash) 보내고, REF는 그만큼 한꺼번에 실행한 뒤 비교한다. 합칠 수 있는 최대 명령 수는 기본 255이고 --squash-size로 바꾼다. 문제를 좁힐 때는 --no-squash로 끄거나, --no-squash-after-instr=N으로 N번째 명령 이후부터만 끈다(difftest/src/test/csrc/common/args.cpp:122-125).

      DiffTest가 증명하지 않는 것

      DiffTest는 기능 정확성을 지킨다. 통과했다고 성능이 좋아졌다는 뜻도, 타이밍이 맞는다는 뜻도 아니다. 그리고 비교는 커밋된 아키텍처 상태만 본다. 그러니 투기적으로 실행했다가 버린 명령이 마이크로아키텍처 상태를 어떻게 바꿨는지는 직접 보지 못한다. 그런 변화가 언젠가 커밋 결과를 틀리게 만들 때 비로소 드러난다.

      emu 실행하기

      빌드한 build/emu는 메모리 이미지(-i)를 0x8000_0000부터 올려 실행한다. 이미지는 바이너리, gz·zstd 압축본, ELF를 모두 받는다. 실행 길이는 사이클 수(-C)나 명령 수(-I)로 자를 수 있다. 성능을 잴 때는 -W로 워밍업 명령 수를 주어, 그 구간이 끝난 뒤의 성능 카운터만 남긴다. 로그와 파형은 -b, -e로 정한 사이클 구간에서만 찍는다. 수십억 사이클 전체를 기록하면 파일이 감당할 수 없이 커지기 때문이다.

      LightSSS: 실패 직전만 다시 돌리기

      몇 시간 돌던 시뮬레이션이 DiffTest 불일치로 멈췄다고 하자. 원인을 보려면 실패 직전의 파형이 필요하다. 그러나 처음부터 파형을 켜고 다시 돌리면 몇 시간이 또 걸리고, 파형 파일도 감당할 수 없이 커진다. LightSSS(Light-weight Simulation SnapShot)는 운영체제의 fork()로 이 문제를 푼다. 시뮬레이션 프로세스가 일정 시간마다 자기 자신을 fork한다. 자식 프로세스는 그 순간의 시뮬레이션 상태를 통째로 품은 채 잠들어 있고, fork의 copy-on-write 덕분에 메모리를 거의 쓰지 않는다. 부모가 실패하면 가장 오래된 자식을 깨운다. 깨어난 자식은 파형과 로그를 켜고 실패 지점까지 다시 달린다.

      가장 오래된 자식만 깨운다 
      // difftest/src/test/csrc/common/lightsss.cpp:83-104 (요약)
int LightSSS::wakeup_child(uint64_t cycles) {
  forkshm.info->endCycles = cycles;
  forkshm.info->oldest = pidSlot.back();
  // only the oldest is wantted, so kill others by parent process.
  for (auto pid: pidSlot)
    if (pid != forkshm.info->oldest) { kill(pid, SIGKILL); waitpid(pid, NULL, 0); }
  forkshm.info->notgood = true;
  forkshm.info->flag = true;   // 잠든 자식이 이 깃발을 보고 깨어난다
  waitpid(pidSlot.back(), &status, 0);
}
      왜 가장 최근 자식이 아니라 오래된 자식인가

      실패에 가장 가까운 스냅숏을 깨우면 다시 돌릴 구간이 더 짧다. 그런데도 오래된 쪽을 깨우는 이유는 무엇일까?

      답 보기

      가장 최근 스냅숏은 실패 직전 몇 초 전일 수도, 거의 실패 순간일 수도 있다. 버그의 원인은 보통 증상보다 앞선다. 잘못된 값이 레지스터와 메모리를 거쳐 늦게 드러나기 때문이다. 그래서 너무 가까운 스냅숏에서 시작하면 원인이 파형 밖에 남을 수 있다. 오래된 쪽을 깨우면 늘 간격 하나 이상의 여유를 확보한다.

      체크포인트와 SimPoint

      RTL 시뮬레이터는 느리다. SPEC CPU 같은 벤치마크 하나를 처음부터 끝까지 돌리려면 수천억 개의 명령을 실행해야 하는데, RTL 시뮬레이터로는 사실상 불가능하다. 그래서 프로그램을 일정 길이의 구간으로 나누고, 구간마다 어떤 기본 블록을 얼마나 실행했는지를 벡터로 기록한다. 비슷한 구간끼리 묶은 뒤 묶음마다 대표 구간 하나만 고른다. 이것이 SimPoint 기법이다. 대표 구간 시작 시점의 아키텍처 상태를 저장한 것이 체크포인트이고, emu는 이를 이미지처럼 불러와 그 지점부터 실행한다. 이때 체크포인트 복원 코드는 --gcpt-restore로 바꿀 수 있다. 각 대표 구간의 CPI에 그 묶음의 크기 비율(가중치)을 곱해 더하면 전체 CPI를 추정할 수 있다.

      $$\widehat{\text{CPI}} = \sum_{j=1}^{k} w_j \cdot \text{CPI}(r_j), \qquad w_j = \frac{|C_j|}{N}$$
      \(N\): 전체 구간 수, \(C_j\): \(j\)번째 묶음, \(r_j\): 그 묶음의 중심에 가장 가까운 대표 구간. kunminghu-v3 CI의 성능 테스트는 체크포인트 목록 JSON에서 벤치마크마다 점(point)과 가중치(weight)를 읽어 골라 쓴다(.github/workflows/ckpt_select.py:13-55).

      체크포인트에서 시작하면 캐시와 분기 예측기가 비어 있다. 그래서 측정 전에 워밍업 구간을 두고(-W), 측정 구간 길이를 정한다(-I). kunminghu-v3의 성능 CI는 체크포인트마다 --max-instr 5000000으로 500만 명령을 돌리고, 출력의 IPC = 줄을 모아 보고서를 만든다(.github/workflows/emu-performance.yml:130-144).

      핵심 정리

      1. make sim-verilog는 mill로 Chisel을 엘라보레이션하고 firtool로 SystemVerilog를 만든다. make emu는 그 결과를 difftest의 Verilator 흐름에 넘겨 C++ 시뮬레이터를 짓는다. 생성된 .sv에는 소스의 git 상태가 주석으로 붙는다.
      2. DiffTest는 커밋마다 DUT와 REF(기본 NEMU)의 아키텍처 상태를 비교해 처음 어긋난 지점에서 멈춘다. 비교 항목은 설계 곳곳에 심은 DiffXXX 프로브가 정하며, 필수 프로브는 ArchEvent, InstrCommit, TrapEvent, CSRState, PhyIntRegState다.
      3. LightSSS는 fork로 스냅숏을 남기고(동시에 최대 2개), 실패하면 오래된 쪽을 깨워 파형과 함께 실패 지점까지 다시 돌린다.
      4. SimPoint는 비슷한 구간을 묶어 대표 구간만 체크포인트로 돌리고, 묶음 크기로 가중 평균해 전체 CPI를 추정한다.
      5. XSDebug·XSPerf·ChiselDB·Constantin은 로그, 카운터, DB 기록, 재빌드 없는 상수 변경을 맡는다. CI는 PR마다 기본 작업 부하와 SPEC06 체크포인트를 돌린다.

      확인 퀴즈

      Q1. DiffTest가 DUT와 REF를 비교하는 시점은?

      ROB가 커밋한 명령을 DiffInstrCommit으로 알리면 REF가 같은 수만큼 실행하고 아키텍처 상태를 비교한다. 투기적 상태는 비교 대상이 아니다.

      Q2. GSIM으로 emu를 지을 때 Makefile이 기본으로 만드는 RTL 형식은?

      Makefile은 sim-chirrtl·gsim 목표에서 CHISEL_TARGET을 chirrtl로 두고, 엘라보레이션 직후의 SimTop.fir에서 멈춘다. GSIM이 CHIRRTL을 직접 읽기 때문이다.

      Q3. LightSSS에서 실패가 일어나면 어떤 자식 프로세스를 깨우는가?

      wakeup_child는 pidSlot.back(), 즉 가장 오래된 자식만 남기고 나머지를 죽인 뒤 깨운다. 원인이 증상보다 앞서는 경우가 많아, 여유 있는 구간을 다시 보기 위해서다.

      Q4. 묶음 3개의 크기가 100, 60, 40개 구간이고 대표 구간 CPI가 각각 0.5, 1.0, 2.5라면 SimPoint 추정 CPI는?

      가중치는 100/200, 60/200, 40/200 = 0.5, 0.3, 0.2. 0.5×0.5 + 0.3×1.0 + 0.2×2.5 = 0.25 + 0.3 + 0.5 = 1.05.

      Q5. kunminghu-v3의 메모리 의존 예측을 다시 빌드하지 않고 실행 중에 끄려면?

      Backend.scala:574의 EnableMdp는 Constantin 레코드다. Constantin으로 빌드한 emu는 실행 때 상수 파일에서 값을 읽는다.
