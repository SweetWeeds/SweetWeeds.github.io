Chapter 11

가상 메모리: TLB와 PTW

프로그램이 쓰는 주소는 가짜다. 운영체제는 프로세스마다 0번지부터 시작하는 넓은 가상 주소 공간을 주고, 그 주소가 실제 DRAM의 어디에 해당하는지는 메모리 안의 페이지 테이블(page table)에 적어 둔다. 적재·저장·인출 명령은 매번 이 표를 거쳐 주소를 바꿔야 한다. 그런데 표를 메모리에서 서너 번씩 읽으면 명령 하나가 수백 사이클을 기다리게 된다. XiangShan은 변환 결과를 TLB에 담아 두고, TLB에 없을 때만 L2TLB의 페이지 캐시와 페이지 테이블 워커(PTW)로 표를 걷는다. 이 장에서는 그 길을 비트 단위로 따라간다.

  • Sv39·Sv48 가상 주소를 VPN 조각과 페이지 오프셋으로 나누고, PTE의 각 비트가 무슨 뜻인지 읽는다.
  • 페이지 워크가 단계마다 PTE를 읽고, 리프나 폴트에서 멈추는 과정을 장난감 페이지 테이블로 직접 걸어 본다.
  • 48엔트리 완전 연관 L1 TLB가 '섹터' 엔트리 하나로 연속 페이지 8개를 덮는 이유를 히트율 실험으로 확인한다.
  • L2TLB의 페이지 캐시 계층(l3·l2·l1·l0·sp)과 PTW·LLPTW·HPTW의 분업을 이해한다.
  • 하이퍼바이저 2단계 변환의 중첩 워크가 최악 24번의 메모리 접근이 되는 이유를 계산한다.
  • U/S 모드, SUM, MXR, A/D 비트가 권한 검사와 페이지 폴트 종류를 어떻게 정하는지 실험한다.

가상 주소를 쪼개는 법

RISC-V의 페이지 기반 가상 메모리는 페이지 크기 4 KiB(12비트 오프셋)를 기본으로 하고, 가상 페이지 번호(VPN)를 9비트씩 잘라 단계별 표의 인덱스로 쓴다. 9비트인 이유는 간단하다. 표 하나가 4 KiB 페이지 한 장이고, PTE 하나가 8바이트라서 한 표에 PTE가 정확히 512 = 29개 들어간다. Sv39는 9비트 조각 3개(39 = 12 + 9×3), Sv48은 4개(48 = 12 + 9×4)를 쓴다. XiangShan 곤명호 v3는 기본 설정에서 Sv48을 켜 두었고(EnableSv48 = true), 하이퍼바이저 확장도 켜져 있다(HasHExtension = true).

PTE는 64비트다. 아래 그림에서 가상 주소와 PTE의 비트 배치를 직접 만져 보자. 곤명호 v3의 물리 주소는 48비트라서 PTE의 44비트 PPN 칸 중 하위 36비트만 쓴다. 상위 8비트에 1이 있으면 접근 폴트(access fault)가 난다.

페이지 워크: 표를 한 칸씩 내려가기

TLB에 변환 결과가 없으면 하드웨어가 직접 표를 걷는다. satp CSR이 가리키는 최상위 표에서 시작해, VPN 조각으로 고른 PTE를 읽는다. PTE의 R·W·X가 모두 0이면 '다음 단계 표를 가리키는 포인터'(non-leaf)이고, 하나라도 1이면 리프(leaf)다. 리프를 만나면 걷기가 끝난다. 리프가 마지막 단계보다 위에서 나오면 그 PTE는 2 MiB, 1 GiB, 512 GiB짜리 슈퍼페이지(superpage)를 뜻한다.

리프인가, 포인터인가, 폴트인가

PTW는 PTE를 받을 때마다 세 가지를 판정한다. 리프면 끝, 접근 폴트나 페이지 폴트면 끝, 그렇지 않으면 한 단계 내려간다. 단계 1에서 아직 포인터라면 마지막(4 KiB) 단계는 LLPTW에게 넘긴다.

XiangShan이 PTE를 받자마자 폴트로 판정하는 조건은 MMUBundle.scala의 isPf에 모여 있다. 예약 비트가 0이 아닐 때, PBMT 값이 3(예약)일 때, 포인터 PTE에 U·A·D·N이나 PBMT가 켜져 있을 때, V=0이거나 W=1인데 R=0일 때가 해당한다. 또 NAPOT 비트(N)는 64 KiB 페이지 하나만 지원한다. 그래서 N=1이면서 PPN 하위 4비트가 1000이 아니거나 리프가 단계 0이 아니면 폴트다. 슈퍼페이지의 PPN 하위 비트가 0으로 정렬되어 있지 않아도 폴트가 난다.

L1 TLB: 섹터 엔트리 48개

페이지 워크를 매번 할 수는 없다. 곤명호 v3는 인출 쪽에 ITLB 하나, 메모리 쪽에 DTLB 셋을 둔다. DTLB는 적재용, 저장용, 프리페처용이다. 모두 48엔트리 완전 연관(fully associative) 구조이고 교체 정책은 PLRU다. 적재 DTLB는 적재 유닛과 일부 프리페처가 함께 쓰고, 프리페치 DTLB는 SMS와 L2 프리페처의 요청을 받는다.

L2TLB: 페이지 캐시와 세 명의 워커

L1 TLB가 놓친 요청은 L2TLB로 간다. L2TLB는 큰 TLB 하나가 아니다. 페이지 테이블의 각 단계를 따로 캐싱하는 페이지 캐시(page cache)가 있고, 그 뒤에 성격이 다른 워커 셋이 붙어 있다.

페이지 캐시무엇을 담나구성덮는 범위
l3Sv48 최상위 포인터 PTE16엔트리 fa · plru엔트리당 512 GiB
l2단계 2 포인터 PTE16엔트리 fa · plru엔트리당 1 GiB
l1단계 1 포인터 PTE, 8개 묶음4세트 × 2웨이 SRAM8 × 2 MiB × 8 = 128 MiB
l0단계 0 리프 PTE, 8개 묶음64세트 × 4웨이 SRAM8 × 4 KiB × 256 = 8 MiB
sp슈퍼페이지 리프16엔트리 fa · plru엔트리당 2 MiB 이상

구성은 MMUConst.scala:44-92의 L2TLBParameters 기본값, 묶음 크기는 같은 파일 305-316행(64바이트 라인 ÷ 8바이트 PTE = 8)에서 왔다.

워커의 분업은 PageTableWalker.scala 첫머리 주석에 그대로 적혀 있다. PTW는 상태 기계 하나로, 리프가 아닌 위쪽 단계(1 GiB, 2 MiB 수준)를 한 번에 하나씩 걷는다. LLPTW(Last Level PTW)는 마지막 4 KiB 단계만 맡되, 기본 6개(llptwsize = 6) 요청을 동시에 처리한다. 마지막 단계는 요청이 가장 많고 서로 독립적이어서 병렬화하기 좋기 때문이다. HPTW는 하이퍼바이저 2단계 변환에서 게스트 물리 주소를 호스트 물리 주소로 바꾸는 G-stage 워크를 맡는다. 페이지 캐시에서 단계 1 포인터까지 적중한 요청은 PTW를 건너뛰고 곧바로 LLPTW로 간다. 그보다 위에서 놓친 요청은 미스 큐를 거쳐 PTW로 간다.

L2TLB에는 단순한 다음 라인 프리페처도 있다. 요청이 페이지 캐시에서 놓치면, 그 VPN이 속한 8페이지 묶음의 다음 묶음을 미리 걷는다(L2TlbPrefetch.scala:45, get_next_line). 최근 요청 4개를 기억해 같은 프리페치를 되풀이하지 않는다.

가상 머신 안의 가상 메모리: 2단계 변환

하이퍼바이저 확장을 켜면 주소 변환이 두 겹이 된다. 게스트 운영체제는 자기 페이지 테이블(vsatp)로 게스트 가상 주소를 게스트 물리 주소(GPA)로 바꾼다. 이것이 VS-stage다. 하이퍼바이저는 또 다른 표(hgatp)로 GPA를 진짜 물리 주소로 바꾼다. 이것이 G-stage다. 문제는 게스트 페이지 테이블 자체도 게스트 물리 주소에 있다는 점이다. 그래서 VS-stage의 PTE를 하나 읽을 때마다 그 PTE의 주소부터 G-stage로 변환해야 한다.

XiangShan은 이 상황을 2비트 s2xlate로 구분한다. noS2xlate(변환 겹침 없음), onlyStage1, onlyStage2, allStage의 넷이다(MMUConst.scala:182-185). 가상화 모드에서 vsatp와 hgatp가 둘 다 켜져 있으면 allStage다. G-stage는 게스트 물리 주소가 2비트 더 넓어서(Sv39x4는 41비트, Sv48x4는 50비트) 최상위 표가 4배 크다.

$$N_{\text{접근}} = n\,(m + 1) + m = (n + 1)(m + 1) - 1$$
\(n\): VS-stage 단계 수, \(m\): G-stage 단계 수. VS-stage의 PTE \(n\)개를 읽을 때마다 그 주소를 G-stage로 \(m\)번 걸어 바꾸고 1번 읽는다. 마지막으로 얻은 게스트 물리 주소도 G-stage로 \(m\)번 더 걸어야 한다. Sv48 위에 Sv48x4면 \(5 \times 5 - 1 = 24\)번, Sv39 위에 Sv39x4면 \(4 \times 4 - 1 = 15\)번이다.
왜 하이퍼바이저 워크 전용 HPTW가 따로 있나

G-stage 워크는 VS-stage 워크 중간중간 끼어든다. PTW와 LLPTW는 각자 게스트 PTE 주소를 바꿔야 할 때 HPTW에 요청을 보내고(hptw_req_arb, L2TLB.scala:170), HPTW의 응답을 받아 자기 워크를 이어 간다. 워커를 나눠 두었기 때문에, 게스트 마지막 단계 요청 여러 개가 LLPTW에서 병렬로 진행되는 동안에도 G-stage 변환을 공유 자원 하나로 처리할 수 있다.

권한 검사와 페이지 폴트

변환에 성공해도 끝이 아니다. TLB는 리프 PTE의 권한 비트를 지금의 특권 모드와 접근 종류에 맞춰 검사한다. 핵심은 TLB.scala의 perm_check다.

모드 검사와 접근별 권한 
// src/main/scala/xiangshan/cache/mmu/TLB.scala:462-468
val ldUpdate    = !perm.a && isLd                    // update A/D through exception
val stUpdate    = (!perm.a || !perm.d) && isSt
val instrUpdate = !perm.a && isInst
val modeCheck = !(mode(idx) === ModeU && !perm.u ||
                  mode(idx) === ModeS && perm.u && (!sum(idx) || ifetch))
val ldPermFail    = !(modeCheck && Mux(hlvx, perm.x, perm.r || mxr(idx) && perm.x))
val stPermFail    = !(modeCheck && perm.w)
val instrPermFail = !(modeCheck && perm.x)

코드를 풀어 쓰면 다음과 같다. U 모드는 U=1인 페이지만 쓸 수 있다. S 모드는 U=1인 페이지를 기본적으로 못 쓴다. sstatus.SUM이 1이면 적재·저장은 허용되지만, 명령어 인출은 SUM과 무관하게 언제나 금지다. 적재는 R=1이어야 하는데, MXR이 켜져 있으면 실행 전용 페이지(X=1)도 읽을 수 있다. 하이퍼바이저의 HLVX 명령은 거꾸로 R이 아니라 X를 요구한다. 마지막으로 XiangShan은 A·D 비트를 하드웨어가 직접 고치지 않는다. A=0인 페이지에 접근하거나 D=0인 페이지에 쓰면 페이지 폴트를 내고, 운영체제가 비트를 세운 뒤 다시 실행하게 한다(코드 주석 "update A/D through exception").

PMP와 PMA: 물리 주소에 대한 두 번째 문지기

페이지 테이블이 가상 주소를 지킨다면, PMP(Physical Memory Protection)는 M 모드가 정한 물리 주소 영역 규칙을 지킨다. PMA(Physical Memory Attributes)는 주소 영역마다 캐시 가능 여부, 원자 연산 가능 여부, 실행 가능 여부 같은 성질을 정한다. 곤명호 v3는 PMP와 PMA를 각각 64개까지 정의할 수 있게 하고, 실제로는 32개씩 구현한다. 단위는 4 KiB다(PMParameters.scala:29-34). 기본 PMA 표는 SoC.scala:58-73에 있다. 엔트리마다 적힌 주소는 그 영역의 끝(TOR 방식)이다. 그래서 PMAConfigEntry(0x80000000000L, c = true, atomic = true, ...)는 0x8000_0000부터 0x7FF_FFFF_FFFF까지의 DDR 영역을 캐시 가능·원자 연산 가능·실행 가능으로 정한다. 같은 주소 지도가 PMA.scala:114-143 주석에 표로 정리되어 있다. TLB는 4 KiB 엔트리에 PMP 판정 결과 일부를 미리 담아 두는 '정적 PMP' 최적화도 쓴다(partialStaticPMP = true).

sfence.vma와 hfence

운영체제가 페이지 테이블을 고친 뒤에는 TLB와 페이지 캐시에 남은 옛 변환을 지워야 한다. sfence.vma rs1, rs2에서 rs1이 0이 아니면 그 주소만, rs2가 0이 아니면 그 ASID만 지운다(TLBStorage.scala:204-230). 가상화 환경에서는 게스트용 hfence.vvma와 G-stage용 hfence.gvma가 따로 있다(hv, hg 비트). ASID는 16비트, VMID는 14비트다. 다만 L2TLB 페이지 캐시의 l1·l0는 ASID·VMID를 3비트로 해시해 저장한다(hashAsidWidth = 3). 해시가 같으면 지울 때 함께 지워질 수 있지만, 그 대가로 SRAM 폭을 크게 아낀다.

이 장에서 다루지 않은 것

곤명호 v3는 기본 설정에서 HasBitmapCheck = true다. 그래서 페이지 워크에 메모리 격리용 비트맵 검사(BitmapCheck.scala, M 모드 CSR mbmc)가 끼어들 수 있다. 이 장의 시뮬레이터는 비트맵 검사가 꺼져 있다고 보고 그렸다.

핵심 정리

  1. Sv39·Sv48은 4 KiB 오프셋 아래로 VPN을 9비트씩 잘라 3단계·4단계 표의 인덱스로 쓴다. 곤명호 v3는 Sv48과 하이퍼바이저 확장을 기본으로 켜고, 물리 주소는 48비트다.
  2. PTW는 PTE마다 리프·포인터·폴트를 판정한다. 예약 비트, 잘못된 PBMT, 포인터의 U/A/D, W만 있는 리프, 정렬 안 된 슈퍼페이지, 64 KiB가 아닌 NAPOT은 페이지 폴트다. PPN이 48비트 물리 주소를 넘으면 접근 폴트다.
  3. L1 TLB는 ITLB 하나와 DTLB 셋(적재·저장·프리페치)이다. 모두 48엔트리 완전 연관이며, 엔트리 하나가 연속 페이지 8개를 덮는 섹터 구조다.
  4. L2TLB는 단계별 페이지 캐시(l3·l2·l1·l0·sp) 뒤에 PTW(위쪽 단계, 하나씩), LLPTW(마지막 단계, 6개 병렬), HPTW(G-stage)를 둔다. 다음 라인 프리페처가 다음 8페이지 묶음을 미리 걷는다.
  5. 2단계 변환의 중첩 워크는 최악 (n+1)(m+1)−1번 메모리를 읽는다. Sv48+Sv48x4면 24번이다.
  6. 권한 검사는 U/S 모드, SUM(인출은 예외), MXR, HLVX 규칙을 따른다. A/D 비트는 하드웨어가 갱신하지 않고 페이지 폴트로 운영체제에 맡긴다.

확인 퀴즈

Q1. Sv48에서 VPN 조각 하나가 9비트인 이유는?

페이지 테이블 한 장은 4 KiB 페이지이고 PTE는 8바이트이므로 512 = 29개가 들어간다. 그래서 단계마다 9비트가 인덱스가 된다.

Q2. PTW가 단계 1에서 읽은 PTE가 여전히 포인터(R=W=X=0, V=1)라면 다음은?

to_find_pte = level === 1.U && find_pte === false.B이면 io.llptw.valid가 켜진다. PTW는 리프가 아닌 위쪽 단계만 걷고, 4 KiB 마지막 단계는 LLPTW가 병렬로 처리한다.

Q3. 섹터 TLB 엔트리 하나가 연속 페이지 8개를 덮도록 만든 근거로 가장 알맞은 것은?

64바이트 캐시 라인에는 8바이트 PTE가 8개 들어 있다. 한 번 읽은 8개를 한 엔트리에 담으면 같은 비용으로 페이지 8개를 덮는다. 페이지 캐시 l0·l1도 같은 8개 묶음을 쓴다.

Q4. 게스트가 Sv48, 하이퍼바이저가 Sv48x4일 때 캐시가 모두 놓친 최악의 중첩 워크는 메모리를 몇 번 읽는가?

(n+1)(m+1)−1 = 5×5−1 = 24. VS-stage PTE 4개마다 G-stage 4번과 PTE 읽기 1번(5×4 = 20), 마지막 GPA의 G-stage 4번을 더하면 24번이다.

Q5. S 모드에서 U=1인 페이지를 SUM=1 상태로 접근한다. 허용되지 않는 것은?

modeCheck는 S 모드에서 U 페이지에 대해 !sum || ifetch면 실패한다. SUM은 적재·저장만 허용하고 인출은 막는다.
