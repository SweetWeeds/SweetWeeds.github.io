Chapter 01

XiangShan 한눈에

XiangShan(香山)은 중국과학원 계산기술연구소와 북경개원칩연구원이 중심이 되어 공개 개발하는 RISC-V 고성능 비순차(out-of-order) 코어다. 하드웨어 기술 언어 대신 Scala에 심은 Chisel로 작성되어 있고, 소스와 검증 환경이 모두 공개되어 있다. 이 장에서는 코어 전체 지도를 펼친다. 앞으로 열다섯 장에 걸쳐 하나씩 열어 볼 블록이 지도 위 어디에 있는지 먼저 짚어 두자.

  • XiangShan 코어를 프런트엔드·백엔드·메모리 블록·캐시·SoC로 나누고, 각 블록이 하는 일을 설명한다.
  • DefaultConfig와 MinimalConfig가 어떤 자원을 얼마나 다르게 쓰는지 소스의 수치로 비교한다.
  • Chisel 소스가 Verilog와 Verilator 시뮬레이터(emu)가 되고, NEMU와 나란히 달리며 검증되는 흐름을 따라간다.
  • ROB 352칸이 '동시에 처리 중인 명령 수'로 얼마만큼인지 감각을 잡는다.
  • XiangShan 저장소를 이루는 하위 모듈과, 이 책의 각 장이 코어 지도 어디에 해당하는지 찾는다.

세대와 이름: 雁栖湖 → 南湖 → 昆明湖

XiangShan의 세대에는 베이징의 호수 이름이 붙는다. 1세대 얀치후(Yanqihu, 雁栖湖), 2세대 난후(Nanhu, 南湖)를 거쳐 지금의 3세대가 쿤밍후(Kunminghu, 昆明湖, 곤명호)다. 이 책이 다루는 코드는 OpenXiangShan 저장소의 kunminghu-v3 브랜치, 커밋 a13efc877(2026-09-28)이다. 본문의 파일 경로와 줄 번호는 모두 이 커밋 기준이다.

코어는 크게 세 덩어리다. 다음에 실행할 명령을 예측하고 가져오는 프런트엔드(Frontend), 명령의 이름을 바꾸고 순서를 바꿔 실행한 뒤 다시 순서대로 마무리하는 백엔드(Backend), 적재·저장을 맡는 메모리 블록(MemBlock)이다. 코어 하나와 전용 L2 캐시를 묶은 것이 XSTile이고, 이 타일이 물리 설계(배치·배선)의 단위다. 여러 타일이 CHI 프로토콜로 공유 L3인 OpenLLC에 붙고, 그 너머에 메모리 컨트롤러가 있다.

계층 구조 
XSTop (src/main/scala/top/Top.scala:91)

L3 종류와 CHI 판본은 빌드할 때 고른다. Makefile:52-53의 ISSUE ?= E.b, LLC ?= OpenLLC가 기본값이고, CHI는 B·C·E.b를, LLC는 OpenLLC와 ZhuJiang을 지원한다. ZhuJiang은 CHI E.b에서만 쓸 수 있다(Makefile:55-66, system/SoC.scala:164-165).

코어 지도

아래 지도는 실제 다이 배치가 아니라 논리 블록도다. 블록을 눌러 보자. 그 블록이 무엇을 하는지, DefaultConfig에서 크기가 얼마인지, 이 책의 몇 장에서 다루는지 아래 칸에 나타난다. 명령은 왼쪽 위 BPU에서 출발해 오른쪽으로 흐르고, 실행을 마치면 ROB에서 순서대로 커밋된다. 적재·저장은 아래쪽 메모리 블록과 캐시 계층으로 내려간다.

Default와 Minimal: 같은 코드, 다른 크기

XiangShan은 하나의 소스에서 여러 크기의 코어를 뽑는다. 크기는 rocket-chip의 Config 체계로 정한다. XSCoreParameters(xiangshan/Parameters.scala)의 기본값이 곧 고성능 구성이다. DefaultConfig는 그 기본값을 그대로 쓰고 캐시 크기만 덮어쓴다. MinimalConfig는 ROB, 큐, 레지스터 파일, 예측기, 캐시를 크게 줄여 시뮬레이터를 빨리 짓고 빨리 돌리기 위한 구성이다. 두 구성은 같은 Chisel 코드에서 나오므로, 구조는 같고 크기만 다르다. Makefile:50의 CONFIG ?= DefaultConfig가 기본값이다.

352개의 명령이 동시에 떠 있다

비순차 코어의 힘은 '얼마나 많은 명령을 동시에 붙잡고 있을 수 있는가'에서 나온다. 캐시 미스로 수백 사이클을 기다리는 적재 명령이 있어도, 그 뒤의 독립적인 명령들은 먼저 실행된다. 이렇게 붙잡아 둘 수 있는 명령의 상한이 ROB(Reorder Buffer) 크기다. DefaultConfig에서 352칸, MinimalConfig에서 48칸이다. 적재 큐와 저장 큐, 이슈 큐, 물리 레지스터도 함께 커야 그 352칸을 실제로 채울 수 있다. 저장 큐는 조금 특별하다. 물리 칸은 64개지만, 디스패치는 그 두 배인 가상 128칸(StoreQueueSize = StoreQueuePhysicalSize × StoreQueueMultiple, Parameters.scala:796)까지 저장 명령을 받아들인다(mem/lsqueue/NewStoreQueue.scala:1544의 allowEnqueue).

$$N_{\text{in-flight}} = \min\!\left(\text{ROB},\; \frac{\text{LQ}}{f_{\text{load}}},\; \frac{\text{SQ}}{f_{\text{store}}}\right)$$
\(f_{\text{load}}, f_{\text{store}}\): 명령 흐름에서 적재·저장이 차지하는 비율. DefaultConfig는 ROB 352, LQ(VirtualLoadQueue) 120, SQ 가상 128칸(물리 64)이다(xiangshan/Parameters.scala:101, 109-110, 114). 적재 비율이 40%면 120/0.4 = 300이라 ROB보다 적재 큐가 먼저 찬다. 25%면 480이라 ROB가 먼저 찬다.

Chisel에서 emu까지

XiangShan의 소스는 Scala 프로그램이다. 이 프로그램을 실행하면 회로가 만들어진다(엘라보레이션(elaboration)). 회로는 FIRRTL이라는 중간 표현을 거쳐 firtool이 SystemVerilog로 내보낸다. 그 Verilog를 Verilator가 C++ 시뮬레이터로 컴파일하면 emu라는 실행 파일이 나온다. emu는 RISC-V 프로그램을 사이클 단위로 실행한다. make emu는 먼저 sim-verilog를 만들고, 빌드 틀은 difftest 하위 모듈에 맡긴다(Makefile:382-386).

emu가 맞게 동작하는지는 DiffTest로 확인한다. emu가 명령을 하나 커밋할 때마다, 같은 프로그램을 돌리는 참조 모델 NEMU도 한 걸음 나아간다. 둘의 PC, 레지스터, CSR, 저장 값을 비교해 하나라도 다르면 그 자리에서 멈추고 어긋난 명령을 알려 준다. 끝까지 같으면 HIT GOOD TRAP이 찍힌다.

명령 (XiangShan/ 안에서)하는 일걸리는 시간
make compScala 소스와 테스트 소스를 컴파일(타입 검사)한다 (Makefile:301)짧음

Verilog 생성은 현재 git log와 git diff를 출력 파일 머리말에 주석으로 남긴다. 다음 빌드는 build/emu를 덮어쓰므로, 결과를 비교하려면 바이너리와 함께 어떤 커밋과 Config로 빌드했는지 따로 적어 두는 습관이 필요하다. 검증과 시뮬레이션 흐름은 15장에서 자세히 다룬다.

XiangShan 저장소를 이루는 것들

XiangShan 저장소에는 코어 본체의 Chisel 코드 말고도 여러 git 하위 모듈(submodule)이 붙어 있다(.gitmodules). 캐시는 XSCache에, 공용 회로는 utility에, 연산기는 YunSuan에, 검증 틀은 difftest에 있다. 각 저장소가 어떤 역할을 하고 서로 어떻게 기대는지 그래프로 보자.

이 책의 지도

마지막으로, 이 책의 각 장이 코어의 어디를 여는지 지도 위에 겹쳐 보자. 장 묶음을 고르면 그 장들이 다루는 블록이 칠해지고, 색이 진할수록 여러 장이 그 블록을 다룬다. 지금 어디를 읽고 있는지 잃어버렸을 때 이 지도로 돌아오면 된다.

핵심 정리

  1. XiangShan은 Chisel로 작성된 오픈소스 RISC-V 비순차 코어이고, 세대는 얀치후 → 난후 → 쿤밍후로 이어진다. 이 책은 kunminghu-v3 브랜치(a13efc877)의 코드를 다룬다.
  2. 코어는 프런트엔드(BPU·FTQ·IFU·IBuffer), 백엔드(디코드·리네임·디스패치·이슈·실행·ROB), 메모리 블록(LSU·LSQ·L1D)으로 나뉜다. 코어와 L2를 묶은 XSTile이 CHI로 OpenLLC(L3)에 붙는다.
  3. DefaultConfig는 ROB 352, LQ 120, SQ 물리 64(가상 128), 정수 물리 레지스터 224, L1D 64KB, L2 2MB, L3 32MB다. MinimalConfig는 폭(8)은 같고 깊이를 줄였다(ROB 48, LQ 24, SQ 물리 16).
  4. 소스 → 엘라보레이션 → firtool → SystemVerilog → Verilator → emu. emu는 DiffTest로 NEMU와 커밋마다 상태를 비교한다.
  5. L3는 기본 OpenLLC이고 빌드 옵션으로 ZhuJiang을 고를 수 있다. CHI 판본(기본 E.b)도 빌드할 때 정한다. 숫자를 말할 때는 늘 어느 Config인지 함께 적는다.

확인 퀴즈

Q1. 물리 설계(배치·배선)의 단위로 쓰이는, 코어와 L2를 묶은 모듈은?

XSTile은 XSCore와 L2Top(CoupledL2)을 묶은 모듈이고(XSTile.scala:39-40) P&R 단위다. 여러 타일이 L3에 붙어 다중 코어가 된다.

Q2. DefaultConfig와 MinimalConfig에서 같은 값은?

디코드·리네임 폭은 둘 다 8이다. ROB는 352 대 48, L2는 2MB 대 128KB, FTQ는 64 대 8이다.

Q3. 명령의 40%가 적재이고 적재 큐가 120칸, ROB가 352칸이다. 적재 큐 때문에 동시에 떠 있을 수 있는 명령 수는 대략?

120 / 0.4 = 300. ROB 352보다 작으므로 적재 큐가 먼저 찬다.

Q4. DiffTest가 증명하는 것은?

DiffTest는 그 실행에서 커밋된 상태가 맞는지를 확인한다. 실행하지 않은 경로의 버그는 잡지 못하고, RTL 등가성이나 타이밍(Fmax)은 형식 검증·합성·STA로 따로 확인해야 한다.

Q5. DefaultConfig에서 저장 큐의 물리 칸은 64개다. 디스패치가 받아들이는 저장 명령의 상한은?

StoreQueueSize = StoreQueuePhysicalSize × StoreQueueMultiple = 64 × 2 = 128(Parameters.scala:796)이고, allowEnqueue는 가상 칸 수가 이 값 이하일 때 참이다.
