Chapter 06

디코드와 리네임

IBuffer를 떠난 명령어는 두 번 다시 쓰인다. 먼저 디코드가 명령어를 하드웨어가 실행할 마이크로 연산(uop)으로 바꾼다. 벡터 명령어 하나는 여러 uop로 쪼개고, 붙어 있는 정수 명령어 두 개는 하나로 합친다. 그다음 리네임이 "x5"처럼 프로그램이 쓰는 이름을 물리 레지스터 번호로 바꾼다. 같은 x5에 차례로 값을 쓰는 두 명령어가 서로 다른 물리 레지스터를 받으면, 둘은 더 이상 순서를 기다릴 이유가 없다. 이 장에서는 곤명호 v3가 사이클마다 8개씩 이 일을 해내는 방법을 따라간다. 분기 예측이 틀렸을 때 이름표를 되돌리는 방법도 함께 본다.

  • 벡터 명령어가 LMUL·SEW·EEW·NF에 따라 몇 개의 uop로 쪼개지는지 계산한다.
  • 디코드 뒤에서 이웃한 두 명령어를 하나로 합치는 28가지 융합 규칙을 실제 어셈블리로 찾아본다.
  • 8개를 한꺼번에 리네임할 때 같은 그룹 안의 앞 명령어 결과를 바이패스로 받는 과정을 단계별로 본다.
  • 이동 명령어를 제거해 물리 레지스터를 공유할 때, 레지스터를 언제 프리 리스트에 돌려주는지 확인한다.
  • 리다이렉트 뒤 리네임 테이블을 스냅샷과 RAB walk로 복구하는 비용을 잰다.

디코드: 명령어를 uop로

곤명호 v3의 디코드 폭과 리네임 폭은 모두 8이다(Parameters.scala:81-82). 정수·부동소수 명령어 대부분은 uop 하나가 되지만, 벡터 명령어는 레지스터 그룹 전체를 다루므로 여러 uop로 나뉜다. 명령어 하나가 만들 수 있는 uop는 최대 8개다(MaxUopSize = 8). 디코드 단계(vector/Decoder/DecodeStage.scala)는 명령어를 '채널'에 배정한다. 채널은 uop를 1개, 2개, 4개, 8개 만드는 종류로 나뉘며, 각 종류마다 8개씩 있다(numM2M4M8Channel = (8, 8, 8)).

몇 개로 쪼갤지는 벡터 설정이 정한다. 데이터 원소 폭 SEW와 레지스터 그룹 배수 LMUL, 그리고 적재·저장 명령어라면 메모리 원소 폭 EEW와 세그먼트 수 NF가 쓰인다. EEW가 SEW와 다르면 메모리 쪽 그룹 배수가 \(\text{EMUL} = \text{LMUL}\cdot\text{EEW}/\text{SEW}\)로 바뀐다. 코드는 둘 중 큰 쪽을 uop 수로 삼는다.

$$n_{\text{uop}} = \max\!\big(1,\ \text{LMUL},\ \text{LMUL}\cdot\tfrac{\text{EEW}}{\text{SEW}}\big), \qquad n_{\text{seg}} = n_{\text{uop}} \cdot \text{NF} \le 8$$
첫 식은 UopNumModule.scala:119-120의 (1.0 max iEmul max dEmul).toInt를 옮긴 것이다. 세그먼트 적재·저장은 여기에 NF를 곱하고, 결과가 8을 넘는 조합은 합법적인 출력이 없다(:73, 출력 0 = 불법). 채널은 1·2·4·8 단위이므로 3은 4짜리, 5~8은 8짜리 채널을 쓴다.

명령어 융합: 둘을 하나로

컴파일러는 "하위 32비트만 남기기"를 slli x1, x1, 32 다음 srli x1, x1, 32로 표현하곤 한다. 두 명령어지만 하는 일은 한 가지이고, 두 번째는 첫 번째 결과를 기다려야 한다. 곤명호 v3의 FusionDecoder는 디코드 출력 중 이웃한 두 명령어(최대 7쌍, DecodeWidth − 1)를 검사한다. 미리 정한 패턴에 맞으면 첫 명령어를 새 연산(예: add.uw)으로 바꾸고 두 번째는 지운다. 그러면 실행 유닛 하나, 물리 레지스터 하나, 의존 사슬 한 고리가 절약된다.

패턴은 28가지다(FusionDecoder.scala:530의 fusionList). 공통 조건이 있다. 두 명령어의 목적지가 같고, 첫 명령어의 목적지가 두 번째 명령어의 원천이어야 한다. 그래야 첫 결과를 버려도 안전하다. 또 목적지가 x0인 HINT 명령어는 합치지 않는다. 여러 패턴이 동시에 맞으면 시뮬레이션 단언(XSError)이 걸리도록 되어 있어, 패턴들은 서로 겹치지 않게 설계되었다.

리네임 테이블과 그룹 안의 바이패스

리네임의 중심은 리네임 테이블(RAT)이다. 아키텍처 레지스터마다 지금 어느 물리 레지스터가 최신 값을 가질 예정인지 적힌 표다. 곤명호 v3는 정수·부동소수·벡터·vl 레지스터마다 RAT를 따로 두고, 각 RAT를 두 벌씩 유지한다(RenameTable.scala:97-104).

  • 추측 테이블 spec_table: 리네임이 사이클마다 고쳐 쓰는 앞선 상태.
  • 아키텍처 테이블 arch_table: 커밋된 명령어까지만 반영한 확정 상태.

명령어 하나를 리네임하는 규칙은 간단하다. 원천 레지스터는 RAT에서 물리 번호를 읽고(psrc), 목적지 레지스터는 프리 리스트에서 새 물리 번호를 받는다(pdest). 그런 다음 RAT의 그 칸을 새 번호로 바꾼다. 어려움은 8개를 한 사이클에 한다는 데 있다. 그룹의 3번째 명령어가 1번째 명령어의 결과를 읽는다면, RAT에는 아직 1번째의 새 번호가 없다. 그래서 그룹 안의 앞 명령어 중 같은 레지스터에 쓰는 가장 가까운 것을 찾아 그 pdest를 바로 가져온다. 이것이 그룹 내 바이패스다(Rename.scala:661-700).

이동 명령어와 크리티컬 패스 
// src/main/scala/xiangshan/backend/rename/Rename.scala:664-680 (주석 발췌)
// How to set pdest: Mux(isMove, psrc, pdest_from_freelist).
// The critical path of rename lies here:
// pdest(N) = Mux(isMove(N), Mux(bypass(N, N - 1), pdest(N - 1),
//                           Mux(bypass(N, N - 2), pdest(N - 2),
//                           ...  rat_out(N))...)),
//                           freelist_out(N))
io.out(0).bits.pdest := Mux(isMove(0), uops(0).psrc.head, uops(0).pdest)

이동 명령어는 새 레지스터를 받지 않고 원천의 물리 번호를 그대로 목적지로 쓴다. 그 원천이 같은 그룹 앞 명령어의 결과라면, 바이패스 사슬이 pdest까지 길게 이어진다. 코드 주석은 이 경로를 리네임 단계의 크리티컬 패스로 지목한다.

프리 리스트와 이동 제거

물리 레지스터 번호는 프리 리스트라는 원형 큐에서 나온다. 리네임이 머리에서 꺼내 쓰고, 커밋이 꼬리에 돌려준다. 돌려주는 번호는 새 명령어가 아니라 덮어쓰인 옛 번호(old pdest)다. 커밋된 명령어가 x5를 p12로 바꿨다면, 그 전에 x5가 쓰던 번호는 더 이상 누구도 읽지 않는다. 곤명호 v3의 프리 리스트는 레지스터 종류마다 따로 있다(Rename.scala:117-120).

이동 제거가 들어오면 문제가 하나 생긴다. mv x7, x6를 리네임하면 x6과 x7이 같은 물리 레지스터를 가리킨다. 나중에 x6을 덮어쓰는 명령어가 커밋될 때 옛 번호를 그냥 돌려주면, 아직 x7이 그것을 쓰고 있다. 흔한 해법은 물리 레지스터마다 참조 수를 세는 것이다. 곤명호 v3는 다른 길을 택했다. 정수 아키텍처 테이블의 32칸 전체를 훑어, 옛 번호를 가리키는 칸이 하나도 없을 때만 돌려준다(need_free).

참조 카운터 대신 전체 비교 
// src/main/scala/xiangshan/backend/rename/RenameTable.scala:159-163
for (((old, free), i) <- (old_pdest zip need_free).zipWithIndex) {
  val hasDuplicate = old_pdest.take(i).map(_ === old)
  val blockedByDup = if (i == 0) false.B else VecInit(hasDuplicate).asUInt.orR
  free := VecInit(arch_table.map(_ =/= old)).asUInt.andR && !blockedByDup
}

같은 사이클에 커밋하는 명령어 여럿이 같은 옛 번호를 내놓으면, 첫 번째만 돌려준다(blockedByDup). 아키텍처 테이블은 커밋된 상태라서, 이 비교는 투기 상태와 무관하게 정확하다.

되돌리기: 스냅샷과 RAB walk

분기 예측이 틀리면 그 뒤에 리네임된 명령어는 모두 무효다. 추측 RAT도 틀린 분기 직후 상태로 돌아가야 한다. 곤명호 v3는 두 장치를 함께 쓴다.

  • RAB(리네임 버퍼, 352칸): 리네임한 uop마다 "어느 아키텍처 레지스터에 어느 물리 번호를 썼는가"를 순서대로 적어 둔다. 복구 때 출발점에서부터 틀린 분기 직전까지 이 기록을 사이클당 8개(RabCommitWidth)씩 다시 적용하며 RAT를 재건한다. 이것이 walk다(rob/Rab.scala:152-160).
  • 스냅샷(최대 4개): 특정 시점의 추측 RAT 전체를 통째로 복사해 둔다(RenameSnapshotNum = 4). 복구할 때 틀린 분기보다 앞선 가장 가까운 스냅샷을 불러오면, walk는 그 지점부터만 하면 된다. 스냅샷이 없으면 아키텍처 테이블(커밋 지점)에서 출발한다(RenameTable.scala:126-131).
스냅샷을 찍는 조건 
// src/main/scala/xiangshan/backend/rename/Rename.scala:766-771
val sameSnptDistance = (RobCommitWidth * 4).U
// notInSameSnpt: 1.robidxHead - snapLastEnq >= sameSnptDistance 2.no snap
val notInSameSnpt = GatedValidRegNext(distanceBetween(robIdxHeadNext, io.snptLastEnq.bits) >= sameSnptDistance || !io.snptLastEnq.valid)
val allowSnpt = if (EnableRenameSnapshot) notInSameSnpt && !lastCycleCreateSnpt && io.in.head.bits.firstUop else false.B
uops.zip(io.in).foreach{ case (uop, in) => uop.snapshot := allowSnpt && FuType.isJump(in.bits.fuType) && in.fire }

스냅샷은 점프 계열 uop가 있는 그룹에서만 찍는다. 직전 스냅샷과 ROB에서 32칸(RobCommitWidth × 4) 이상 떨어져 있어야 하고, 바로 앞 사이클에 찍지 않았어야 한다. 네 칸이 다 차 있으면 찍지 않는다(CtrlBlock.scala:777).

스냅샷이 네 개뿐인 이유

스냅샷 하나는 정수·부동소수·벡터·vl RAT 전체와 프리 리스트·RAB 포인터의 사본이다. 개수를 늘리면 복구는 빨라지는데 왜 넷에서 멈췄을까?

답 보기

스냅샷은 플립플롭으로 된 통째 사본이다(Snapshot.scala의 Reg(Vec(RenameSnapshotNum, …))). 하나를 늘릴 때마다 RAT 전체 크기만큼 면적이 늘고, 복구할 때 고르는 MUX도 넓어진다. 위 그림에서 보듯 분기는 대부분 커밋 지점 가까이에서 해결된다. 그래서 앞쪽 몇 개만으로도 평균 walk가 크게 준다. 나머지는 사이클당 8개씩 걷는 walk로 충분하다는 절충이다.

핵심 정리

  1. 디코드·리네임 폭은 8이다. 벡터 명령어는 \(\max(1, \text{LMUL}, \text{EMUL})\)개(세그먼트면 × NF, 최대 8)의 uop로 쪼개진다.
  2. FusionDecoder는 이웃한 두 명령어를 28가지 패턴으로 합친다. 공통 조건은 같은 목적지, 첫 결과가 두 번째의 원천, x0이 아닌 목적지다.
  3. RAT는 추측·아키텍처 두 벌이다. 한 그룹 8개를 리네임할 때 앞 명령어의 결과는 그룹 내 바이패스로 받는다. 이동 명령어는 원천 번호를 공유하고 디스패치를 건너뛴다.
  4. 프리 리스트는 정수 223·부동소수 224·벡터 81·vl 31칸이다. 정수 레지스터는 참조 카운터 대신 아키텍처 테이블 전체를 비교해, 아무도 가리키지 않을 때만 돌려준다.
  5. 복구는 가장 가까운 스냅샷(최대 4개, 32칸 이상 간격, 점프 uop에서) 또는 아키텍처 테이블에서 출발해, RAB를 사이클당 8개씩 다시 적용하는 walk로 마무리한다.

확인 퀴즈

Q1. SEW 16, EEW 64, LMUL 1인 인덱스 적재는 몇 개의 uop가 되는가?

EMUL = 1 × 64/16 = 4. max(1, 1, 4) = 4개다.

Q2. slli a0, a1, 3 다음 add a0, a0, a2는 무엇으로 합쳐지는가?

첫 명령어의 목적지 a0가 두 번째의 목적지이자 원천(rs1)이다. slli 3 + add 패턴(slli3_add)이 맞아 sh3add가 된다.

Q3. mv x7, x6(이동 제거) 뒤에 add x6, x1, x2가 커밋되었다. x6의 옛 물리 번호는?

need_free는 아키텍처 테이블 전체가 옛 번호를 가리키지 않을 때만 참이다. x7이 같은 번호를 쓰고 있으므로 돌려주지 않는다. 나중에 x7이 덮어써질 때 그 커밋에서 돌려준다.

Q4. 스냅샷 없이 복구할 때 walk는 어디서 시작하는가?

리다이렉트 때 추측 테이블을 arch_table(또는 스냅샷)로 바꾸고, RAB의 해당 구간을 사이클당 8개씩 다시 적용한다. 스냅샷이 있으면 출발점이 그만큼 가까워진다.

Q5. 리네임 그룹의 5번째 명령어가 2번째 명령어가 쓴 x9를 읽는다. psrc는 어디서 오는가?

같은 그룹의 앞 명령어가 쓴 레지스터는 RAT에 아직 반영되지 않았다. 그래서 가장 가까운 앞 명령어의 pdest를 바이패스로 받는다.
